# Forkscape recording format, version 1

A recording is an ordered log of what a process tree did to its memory: forks, mappings, page faults, descriptors, and markers such as Gunicorn hooks or requests. Forkscape replays it through the same scene, flat view, chart, ledger, and RSS/PSS comparison as its scenarios, grouping the events into stages and the stages into phases.

Forkscape also reads [`forkscape.capture.v1` sampled captures](capture-format.md). Those files contain measured process and cgroup aggregates without page addresses or fault events. The same file picker opens them in the measured capture viewer at `/capture.html`, where Flat and 3D views can be switched; they cannot drive this page-level replay.

The picker also recognizes [`forkscape.node.v1` node recordings](node-recording-format.md) and raw Kubelet `/stats/summary` JSON. They open in `/node.html` with aggregate 3D columns, Flat charts, and sample stepping. Node counters do not provide page or socket identities.

Any recorder can write one: an eBPF tracer, a `/proc` sampler, `strace` post-processing, or a script. [`examples/recording/`](../examples/recording/README.md) has four reference examples, one for each combination of bpftrace or an unprivileged `pagemap` sampler with a workload on the host or in a container. The file is read in the browser and is never uploaded. It may be gzip-compressed (`.json.gz`), which shrinks a recording about tenfold.

The [synthetic example](../public/recordings/synthetic-gunicorn-boot.json) (`#recording/sample`) ships with the app. It is generated by [`scripts/make_sample_recording.ts`](../scripts/make_sample_recording.ts). Real recordings belong under `local/`; choose them from disk in **Replay telemetry**.

## Container: the Trace Event Format

A recording is a [Trace Event Format](https://docs.google.com/document/d/1CvAClvFfyA5R-PhYUmn5OOQtYMH4h6I0nSsKchNAySU) file, the JSON that Perfetto and `chrome://tracing` read. The same file opens in [ui.perfetto.dev](https://ui.perfetto.dev) as a raw timeline, which helps when checking what a recorder wrote. Forkscape accepts three forms:

- a JSON object with a `traceEvents` array;
- a JSON array of events, which a streaming writer may leave unclosed, with or without a trailing comma;
- one event per line (NDJSON), which is the easiest form for a tracer that prints as it goes.

Every event is an object with:

| Field | Meaning |
| --- | --- |
| `ph` | Event type: `i` (instant), `X` (complete slice, with `dur`), `B`/`E` (slice begin and end), `C` (counter), or `M` (metadata). Other types are counted and ignored. |
| `name` | What happened, from the vocabulary below. |
| `ts` | Time in microseconds, from any fixed origin. Fractions are allowed. Events need not be in order; they are sorted by `ts`, keeping file order for ties. |
| `pid` | The process the event belongs to. |
| `tid` | Optional. The thread that acted; used for `fork` and `lock`. |
| `cat` | Optional. A category, shown in marker labels, such as `gunicorn`. |
| `args` | Fields specific to the event. |

## Header

The first metadata event named `forkscape` is the header. It is required. Put it first so streaming writers emit it before anything else:

```json
{"ph":"M","name":"forkscape","pid":0,"args":{"version":1,"page_size":4096,"title":"Gunicorn boot, preload, 4 workers","source":"bpftrace on labctl Ubuntu 24.04","captured_at":"2026-11-02T10:00:00Z","kernel":"6.8.0"}}
```

In the object form, the header may instead sit at `otherData.forkscape`.

| Field | Required | Meaning |
| --- | --- | --- |
| `version` | yes | `1`. |
| `page_size` | no | Bytes per page, a power of two from 1024 to 2097152. Default 4096. |
| `title` | no | Shown as the recording's heading. Defaults to the file name. |
| `source` | no | How it was recorded, shown under the title. |
| `synthetic` | no | `true` for generated data, which the app labels as synthetic. |
| `stage_gap_ms` | no | A pause this long between events starts a new stage. Default 50. |
| `captured_at`, `kernel`, `host`, `runtime`, `config`, `notes` | no | Shown as facts about the recording. Strings or flat objects. |

`process_name` metadata events (`{"ph":"M","name":"process_name","pid":1236,"args":{"name":"gunicorn: master"}}`) name processes in the flat view.

## Events that change the model

Instant events (`"ph":"i"`). Addresses are numbers or hex strings such as `"0x7f2000100000"`; lengths are bytes.

| `name` | `pid` | `args` | Effect |
| --- | --- | --- | --- |
| `exec` | the process | `comm`, `ppid` | Starts tracking a process, or replaces a tracked process's address space. The first process seen is the master; every later process must descend from it, through `fork` or an `exec` whose `ppid` is tracked. Events from other processes are counted and ignored. |
| `fork` | the parent | `child`; optional `vfork` | The child gets a copy of the parent's mappings and page table, following the kernel's rule: private mappings that hold anonymous pages are copied and shared copy-on-write; other pages fault back in. Only the forking thread survives. |
| `thread` | the process | `new_tid` | Starts a thread. |
| `mmap` | the process | `addr`, `len`; optional `file`, `offset`, `perms`, `shared`, `writable`, `name` | Maps a region. Nothing is resident until it is touched. With `file`, the region is file-backed, and mappings of one file share its page cache. `perms` takes the `/proc/<pid>/maps` form, such as `rw-p` or `r--s`. Without `perms`, anonymous memory is writable and file memory read-only. A new mapping replaces any it overlaps, as `MAP_FIXED` does. Report `brk` growth as an `mmap` of the added range. |
| `munmap` | the process | `addr`, `len` | Unmaps a range, which may be part of a region. |
| `mremap` | the process | `addr`, `old_len`, `new_len`, `new_addr` | Moves and resizes a range, as glibc's `realloc` does for large blocks. Its resident pages move with it without faults; a shrink frees the cut-off part, and growth is mapped but not resident. |
| `madvise` | the process | `addr`, `len`, `advice` | `dontneed`, `free`, or `remove` (with or without the `MADV_` prefix) drop resident pages; other advice is ignored. |
| `fault` | the process | `addr`, `write`; optional `around`, `kernel` | One page fault. The replay classifies it as the kernel would: a first write to anonymous memory allocates a zeroed page; a first read maps the zero page; a file page comes from the page cache; a write to a shared or file-backed private page copies it; a write to a page the process alone holds reuses it. `around: true` marks a page the kernel mapped beside a file fault (fault-around), which is replayed as a read and counted separately in the caption. `kernel: true` marks a fault taken while the kernel wrote to user memory, as `read()` does. |
| `open` | the process | `fd`, `object`, `kind`, `name` | Opens a descriptor. `object` identifies the kernel object (an inode, or a hashed socket address), so descriptors in several processes can share one. `kind` is `file` or `socket`. |
| `close` | the process | `fd` | Closes a descriptor. |
| `lock`, `unlock` | the process | `lock` | A thread (`tid`) takes or releases a named lock. |
| `exit` | the process | | The process exits and its memory is released. |
| `oom_kill` | the victim | | The OOM killer stops the process. |
| `reap` | the parent | `child` | The parent reaps a zombie. Without any `reap` events, each worker is removed as it exits. |
| `limit` | any | `bytes` | The cgroup memory limit, drawn on the chart. |
| `lost` | any | `count` | The recorder dropped events here. The stage says so. |

A fault outside every recorded mapping, for example in memory mapped before recording started, gets a region named “unrecorded”, treated as a private file mapping. To name those regions, emit a process's existing mappings from `/proc/<pid>/maps` as `mmap` events right after `exec`.

## Measurements

Counter events (`"ph":"C"`) are charted beside the replay's own figures, so drift between the two shows:

| `name` | `pid` | `args` |
| --- | --- | --- |
| `memory` | the process | `rss_kib`, `pss_kib` (from `/proc/<pid>/smaps_rollup`) |
| `cgroup` | any | `memory_current_kib` (from the cgroup's `memory.current`) |

## Markers, stages, and phases

Any other event is a marker. An instant marker starts a stage; so does an outermost slice (`X` or `B`) such as `{"ph":"X","name":"request","args":{"method":"GET","path":"/scan"}}` or a top-level `import` with `args.module`. A slice nested inside another one of the same process annotates its stage instead, so a Django import with hundreds of nested imports is one stage.

A stage also starts at every `exec`, `fork`, `thread`, `exit`, and `oom_kill`, and after a pause of `stage_gap_ms` between events. Faults, mappings, and descriptors in between are summarized in the stage's caption with exact page counts.

Phases group stages. A `phase` event (`args.label`) starts a phase. Without any, a recording that forks has three: *Startup* until the first fork, *Forking workers* until a second passes without a fork or a request starts, and *Workers running* after that.

## How the replay is drawn

- **Exact figures.** Every event is applied to a page-level ledger, which gives the chart's Σ RSS and Σ PSS and the counts in each caption. The scene's labels, flat cards, ledger panel, and inspector show the ledger's per-process RSS, PSS, and USS too, not counts of tiles.
- **Merged mappings.** A private anonymous mapping placed right next to one with the same name and permissions joins it, as the kernel merges virtual memory areas. Each `brk` and each allocator arena would otherwise be a mapping of its own.
- **Tiles.** The scene draws each process's touched span of each mapping as tiles. A tile stands for a power-of-two number of pages, the smallest that fits the busiest process into 24 tiles, the most a 3D deck shows. The panel offers 48 and 96 for finer detail in the flat view. A tile is drawn resident once half its pages are, and copied once its process has copied half of them, so the scene can lag the exact figures by up to half a tile.
- **Groups.** A real process maps hundreds of regions, too many to draw one by one. Then each process's mappings are drawn in groups by kind, laid end to end: code and read-only files, private file data, the heap, anonymous memory, the stack, and shared memory. Mappings a process makes after fork are grouped apart from those it inherited. The replay groups only when drawing each mapping alone would need tiles more than four times as large.
- **Untouched mappings** are not drawn, and drawn mappings span only their first to last touched page.
- **Moments that come together** share a stage. Requests, exits, or the same marker within 10 ms of each other lead one stage, such as “Workers 2 and 3 each handle a request: GET /scan.” A request just after a pause leads the stage the pause started, so a connection's accept and its request read as one. A pause-started stage that maps, frees, and opens nothing and changes Σ RSS and memory in use by less than 64 KiB is folded into the next stage.
- **Sampled recordings** work the same way. A recorder that infers events from snapshots, such as the `pagemap` sampler, places each snapshot's changes at one time, so their order within it is the recorder's inference; its `source` says so.
- **Measured lines** come from samples, so they trail stages shorter than the sampling interval. `smaps_rollup` divides a page shared with processes outside the recording, such as a library's code, among all of them, so measured Σ PSS can be lower than the replay's.
- **Not modelled yet:** readahead, transparent huge pages, swap, `mprotect`, `MADV_DONTFORK`, and page-cache pages that outlive their last mapping.

## Limits

A file can be up to 64 MiB and 2,000,000 events, with at most 64 processes running at once. A recording of 340,000 events and 21 MB replays in about a second and a half.

## Producing a recording

[`examples/recording/README.md`](../examples/recording/README.md) lists the probes the bpftrace examples use for each event, and how the `pagemap` sampler infers events from snapshots. Other recorders can use these sources:

| Event | Typical source |
| --- | --- |
| `exec`, `fork`, `exit` | `sched:sched_process_exec`, `sched:sched_process_fork`, `sched:sched_process_exit` |
| `mmap`, `munmap`, `madvise` | `syscalls:sys_enter_*`/`sys_exit_*` pairs (the address comes from `mmap`'s return value); `/proc/<pid>/maps` at exec |
| `fault` | `exceptions:page_fault_user` on x86-64 (`error_code` bit 1 is a write), or a kprobe on `handle_mm_fault` |
| `open`, `close` | `syscalls:sys_exit_openat`, `socket`, `accept4`, `sys_enter_close` |
| `memory`, `cgroup` | a sampler reading `smaps_rollup` and `memory.current` |
| markers | Gunicorn server hooks, request middleware, or CPython import markers, timestamped with `CLOCK_MONOTONIC` like the kernel events |
